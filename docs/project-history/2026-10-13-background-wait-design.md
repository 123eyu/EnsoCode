# 后台任务「一直卡着」：参考整合与方案对比

> 2026-10-13 · Anran · 待林经理评审选型。只读代码与同类项目源码，未复现、未改代码。
> 配套原型：`2026-10-13-background-wait-mockup.html`（静态演示，不是工程交付）。

## 1. 问题

用户反馈「一直卡着」，截图为「子代理 · 等待 · 数据…」+「生成中… 21m24s」。

根因（代码事实）：

| # | 现象 | 位置 |
|---|------|------|
| 1 | 子代理等待不写 `timeoutMs` 就无限等，上限可填 24h；`spawn/send wait:true` 同样无限等 | `src/main/services/agentService.ts:500`、`src/main/ipc/agent.ts:813,830`、`src/agent/subagent.ts`（`timeoutMs` max 86400000） |
| 2 | 用户插话只把前台 shell 转后台，不打断子代理等待、`task_output` 阻塞读（最长 10 分钟） | `src/agent/supervisor.ts:1389,1422`、`src/agent/backgroundTasks.ts` `read()` |
| 3 | 子代理做完一轮本就会自动通知主代理，等待多半没必要；但工具说明没劝阻 | `src/agent/supervisor.ts:3152` |
| 4 | 等待行只有总时长，看不到子代理在干什么，也没有「不等了」 | `TimelineRow.tsx` subagent wait 行 |

顺带的体验问题（同一主题，非本次根因）：

- 前台命令 600s 才自动转后台（同类 10–120s）。
- 后台任务结束 5s 后从任务栏消失；超过 10 个清掉已完成；界面只看末尾 8000 字；没有完整日志入口。
- 没有 dev server 就绪判断；没有防连环唤醒上限；任务结束无系统通知。

我方已有且领先的：用户手动转后台、用户停止后告诉模型别重跑、空闲唤醒/忙时搭车通知与去重、拒绝 `&`、按进程组停止。

## 3. 方案

### A 止血（参考 pi-desktop / deepchat）

- 用户插话立即结束所有阻塞等待（子代理 wait、spawn/send wait:true、`task_output` 阻塞），返回「用户插话，子代理继续运行，结束会通知你」。子代理不停。
- 等待默认 10 分钟、上限 15 分钟；到时返回各子代理状态，子代理继续跑。
- 界面不动。
- 约 1 人日（Jason）。
- 好处：改动小，直接消除「怎么说都没反应」。不足：没插话时仍可能干等 10 分钟；用户看不到子代理在干嘛。

### B 不阻塞为默认（参考 omp / ZCode / pi-desktop）— **推荐**

A 全部，加：

- 工具说明与提示改为「子代理做完会自动通知你；除非下一步必须用它的结果，否则不要等」。
- 超时返回的是进度心跳：每个子代理当前状态、在跑的工具、已用时。
- 等待行改为可展开：显示等的是哪几个子代理、各自正在干什么、已用时；加「不等了」按钮（同现有命令「转后台」，子代理继续跑，模型收到用户已转后台的说明）。
- 约 2.5 人日（Jason 1.5 + 欧阳 1）。
- 好处：既少阻塞，阻塞时用户也有掌控。不足：提示词效果需用两家模型真机验证。

### C 统一后台工作面板（参考 ZCode / deepseek-harness）

B 全部，加：

- 输入框旁「后台 N」角标（shell 任务 + 子代理分类计数），点开侧栏面板：运行中 / 已结束两段，展开看实时输出，可停止、打开完整日志。
- 任务结束不再 5 秒消失，进「已结束」，可手动清除；重启后残留标「App 退出时已停止」。
- 约 5–6 人日（欧阳为主）。
- 好处：一并解决「任务结束找不到输出」。不足：与现有 TaskBar 重叠，需定 TaskBar 去留；手机端投影另算。

### 独立小项（可与任一方案并行，单独拍板）

| 项 | 参考 | 估时 | 风险 |
|----|------|------|------|
| 前台自动转后台 600s → 120s | ZCode / deepseek-harness 120s、omp 60s | 0.5 人日 | 跑 2–10 分钟的测试也会转后台，模型需等通知 |
| 防连环唤醒（连续唤醒 N 次后暂停并在界面提示） | deepseek-harness | 0.5–1 人日 | 阈值需定 |

| dev server 就绪探测（日志关键字/端口） | omp、lody | 3+ 人日 | 暂不建议，先观察 |

## 4. 建议

先做 **B**：根因是阻塞等待，B 用较小代价同时解决「卡」和「看不见」。C 等 B 上线、收到「找不到输出」类反馈后再排。小项里「600s → 120s」与 B 同批最划算。

## 6. 验收要点

- 子代理慢或卡住时，用户插话后模型在一轮内响应，子代理不被停止，结束后仍收到通知且不重复。
- 等待超时返回进度而非失败；不写超时也不会超过上限。
- 「不等了」后模型不再重新等待同一子代理（除非用户要求）。

## 7. 实现备注

- spawn/send `wait:true` 不带 `timeoutMs`，同样按默认 5 分钟结算，超时回执带 `pending` 进度。
- 上限只管模型调用；workflow 的 `agent()` 超时后循环 wait，直到成员结束。
- 交付去重：Run 被 wait 回执（含超时 / 插话）、report、stop、dismiss 带回即算已交付；`until:'all'` 等待中先结束的 Run 交给那次回执，不单独通知。
- worker 取消分两种：`detach`（插话 / 不等了，回执照常给模型）与 `abort`（本轮中止，回执被丢）；`abort` 时已结束的 Run 不算交付，改发通知。
- 至少两家模型真机验证提示词是否减少阻塞等待。
