# 委派改造最终设计（#42 实施依据）

状态：定稿，已经 TechLead 阿轩评审（seq455）并补入第十二节，未改生产代码。整合 #40 产品设计（`2026-10-08-delegation-redesign.md`、`-mockup.html`）、#41 技术方案（`2026-10-08-delegation-redesign-tech.md`）、#44 DeepSeek-Bot 源码对照（`2026-10-08-deepseek-bot-delegation-research.md`）。三份原稿保留作依据；**与本文冲突处以本文为准**。原 #39 并入。

## 一、一句话

委派从「群主私下调一次子代理」改为「看板任务为主体、成员接着自己的上下文干活、卡住是正式状态、关键节点在群里公开」。任务管状态和验收，`Delegation` 记录就是一次执行，会话按「任务 × 成员」延续。

## 二、三层模型

| 层 | 实体 | 职责 | 权威源 |
| --- | --- | --- | --- |
| 任务层 | `GroupTask`（新增 `runs` 摘要、`sessions`、`blocked` 状态、`blockedNeed/blockedStreak`） | 归属、状态、验收 | 群任务存储 |
| 执行层 | `Delegation`（新增 `trigger`、`startedAt`、`blocked`、`appends`，状态加 `blocked`） | 一次执行：排队、开工、交付/卡住/失败、计时、结果回传 | `delegations.jsonl` |
| 会话层 | 子会话 `childConversationId` | 模型上下文 | pi worker jsonl |

不新造「run」实体；不引入第二套存储或自建压缩引擎。

**会话隔离键（#44）**：Main 用「任务所属根群 + 任务真实 id + 成员 botId」从权威记录推导，不接受调用方传会话路径，不按展示 `#N` 或 botId 单独建缓存。跨任务、跨群绝不复用；同任务同成员可续。不自动把成员私聊摘要或其他会话塞进任务会话（DeepSeek-Bot 首次群 prompt 带私聊 brief 的做法不采用）。

## 三、状态流转

任务：

```text
 待办 ──派活/认领──▶ 进行中 ──交付──▶ 待验收 ──通过──▶ 完成
  ▲                 │  ▲  ▲              │
  │      卡住/失败   │  │  └─退回返工/追加─┤
  │                 ▼  │ 回复/重试        │
  │               卡住 ─┘                 │
  └──改派/取消执行─┴───────退回待办───────┘
 执行人 = 发起方时交付直接完成（#21）；任意未完成状态可被人取消。
```

执行：`排队 → 执行中 → 交付 | 卡住 | 失败 | 已取消`。追加和人插话是当前执行内的 steer，不产生新行；回复、重试、返工、待验收追加各开一次新执行，接同一会话。

## 五、送达与结算（#44 补强，P3 验收硬条件）

- 追加带 `deliveryId`，同 id 重发不重复执行；区分 accepted / deferred / failed，`delegate` 最多等 10 秒回执。
- worker 回合收尾时收到的 deferred 输入归当前执行：`onTurnFinished` 时子会话仍忙就不结算，跑完再结算。
- 「忙就不结算」有上限：执行到期（第四节第 7 条的合并期限）时强制结算，未跑完的追加按失败记入 `appends[i].ok=false` 并在结果里写明，不能让会话永远收不了尾。
- 已失败的追加不能让执行永远忙；终态后到达的追加按第四节第 5 条开新执行。
- 结果回精确 `parentConversationId` + batch，不按成员身份回「当前私聊」；不能串群、漏回或重复回。
- 必测：排队中追加、收尾 deferred、重复投递、终态后追加、换批次 keep/取消、重启恢复、并发连派。
- 不照搬 DeepSeek-Bot：成员私聊收所有消息、followup 当 steer、单槽 pending 回信归属。

## 六、公开进度

- 新时间线条目 `kind:'progress'`（`started/blocked/delivered`），由 Main 在状态转换时按模板以成员名义写，成员不调工具；替换原来对应的三条 system 行。
- 文案：开工「开工 #N『标题』」（续跑「接着做 #N」）；卡住「#N 卡住了，缺：…」并 @等待的人；交付「交付 #N：结果首行」。验收结论由群主或你发一条。
- 刷屏控制：每次执行最多 2 条；60 秒内结束的不发开工；追加、排队、重试、工具调用不发；深度 2 只发卡住。
- 不触发路由和选人：不进 `begin()/advance()`，智能选人不读，不解析 @，不计轮次。全员上下文可见、单行，嫌吵再收窄到群主。
- 挂了任务的委派结果卡在群里默认折叠，避免和「交付」重复。
- 写到发起委派的话题，看板按根群存。

## 十一、风险

1. 模型不调 `report_blocked` 而在结果里提问：按交付进待验收，靠退回兜底；真机专项测。
2. 调了 `report_blocked` 不收尾：5 分钟兜底，停止原因与人工停止区分。
3. batch 转移后早一轮少一条结果，要在最近一轮看到；`delegate` 返回 `merged:true` 已告知群主。
4. 自动建卡让看板变多：仅群聊深度 1。
5. 失败改为「卡住保留负责人」后，失败任务不再自动回待办，需要人点改派或取消。

## 十二、评审补充（阿轩 seq455，开工前必须满足）

1. **卡住分两种原因**：`blockedReason: 'need' | 'failed'`。界面分别显示「卡住·缺 X」「卡住·执行失败：原因」。`failed` 只能重试/改派/取消，群主不能代答，不计连续 3 次护栏；否则网络连断 3 次就被锁成只能人解。
2. **软停止路径（P4 新增，单独测试）**：现有 `stopConversation`（`botSessionHost.ts:612`）会 `cancelQueued` 取消该会话全部排队消息并走停止级联，不能用于卡住兜底。新路径只中止当前回合；排队中的追加转为下一次执行，不丢；不取消子委派；停止原因与人工停止区分。
3. **忙不结算有上限**：见第五节，到期强制结算。
4. **每期合入 main 即可发版**：每期都必须单独完整可用，做不到的部分默认不生效（例如 P1 只有自动建卡和执行记录也要闭环；`report_blocked` 在 P4 完整前不挂载、`blocked` 不写入）。期内不得留「半开」入口。
