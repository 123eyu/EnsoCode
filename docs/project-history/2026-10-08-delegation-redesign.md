# #40 委派改造：以看板任务为主体的同事协作（产品设计）

状态：产品设计 + 可交互 mockup（`2026-10-08-delegation-redesign-mockup.html`），未改生产代码，未立项实现。技术方案见 Jason #41，本文「待技术确认」逐条交给他。参照：`2026-10-06-bot-competitor-research.md` 第⑤节 Multica。原 #39（同发起方追加即插入）并入本文。

## 结论先说

1. **任务是主体，执行是记录。** 每次委派都挂在一张看板任务上（没给 `taskId` 就自动建卡）。任务卡下列出「历次执行」：谁、因为什么开始（派活 / 追加 / 回复后继续 / 退回返工 / 重试）、结果、耗时、查看过程。
2. **同一任务 + 同一成员 = 同一条会话。** 返工、卡住后继续、在待验收时追加，都接着上次的上下文跑，不开空白会话。查看过程看到的是一条连续对话，中间用「第 N 次执行」分隔。
3. **同一发起方追加 = 插进当前执行（steer）**，不排队、不另起执行；结果只回一次；期限取两者中较长的。
4. **「卡住」是正式状态。** 成员用专门的出口写明「缺什么、等谁」，本次执行随即结束、释放并发名额。看板显示「卡住·缺 X」。人或发起方在这张任务下回复，同一成员自动接着跑。
5. **群里只发三类节点：开工、卡住、交付**，以成员自己的名义、一两行。过程（调工具、追加、重试）只留在任务卡和查看过程里。群主照常收到结果并按 #21 验收，验收结论由群主发一句。
6. 保持不变：#21 待验收、#28 人工插话（转入当前执行）、#19 计时（从真正开工起算，排队不计）、#29 跨聊天并行。不做全员唤醒。

## 一、用户场景

| 场景 | 今天的问题 | 改造后 |
| --- | --- | --- |
| 你让群主安排一件事 | 委派是群主私下的子调用，群里只看到一张委派卡，成员干到哪不知道 | 看板自动出一张卡；成员在群里说「开工」「卡住」「交付」 |
| 成员缺信息 | 只能在结果里问一句然后算「做完」，或者一直挂着占名额、最后超时 | 成员报「卡住·缺 X」，名额释放；你回一句它就接着干 |
| 结果不满意 | 退回后清掉执行人，下次派活是全新会话，前面的上下文丢了 | 退回给原成员返工，接着原会话改 |
| 群主想补一句要求 | 再派一次 → 排队或并行一条新会话，结果回两次 | 插进正在跑的那次执行，结果只回一次 |

目标用户：在桌面群聊里指挥一组 Bot 成员的单人用户；手机端主要是出门时看一眼进度、回一句卡住的问题。

## 二、状态流转

### 任务状态（看板列）

```text
            派活 / 认领              交付                 通过
  [待办] ─────────────▶ [进行中] ──────────▶ [待验收] ──────────▶ [完成]
    ▲                    │   ▲  ▲                 │
    │        报卡住 / 失败 │   │  └─ 退回（返工）/ 追加 ┤
    │                    ▼   │ 回复 / 重试           │
    │                  [卡住] ┘                      │
    │                    │                          │
    └── 改派 / 取消执行 ───┴────── 退回并改派 ─────────┘

  执行人 = 发起方时，交付直接进「完成」（#21）；任意未完成状态可被人作废为「已取消」（现有）。
```

| 转换 | 触发 | 说明 |
| --- | --- | --- |
| 待办 → 进行中 | 派活（含自动建卡）、成员认领 | 产生「第 1 次执行」。排队时也算进行中，卡片角标「排队」，计时不走（#19） |
| 进行中 → 卡住 | 成员调用「报卡住」出口；或执行失败 / 超时 / 被拒 | 本次执行结束，释放名额。成员自报写「缺 X」；系统失败写「执行失败：超时」等原因 |
| 卡住 → 进行中 | 人或发起方在任务下回复；或点「重试」 | 同一成员新开一次执行，接上下文。回复正文和卡住时的提问一起作为本次输入 |
| 卡住 → 待办 | 人点「改派」或「取消执行」 | 清执行人（保持现有退回语义） |
| 进行中 → 待验收 | 成员交付（正常结束） | 执行人 ≠ 发起方时；执行人 = 发起方直接进「完成」（保持 #21） |
| 待验收 → 完成 | 发起方或人「通过」 | 保持 #21 的验收人范围 |
| 待验收 → 进行中 | **退回（返工）**，必须填理由 | 同一成员新开一次执行，触发来源「退回」，带退回理由，接上下文 |
| 待验收 → 进行中 | 发起方 / 人追加要求 | 视同返工，但来源记「追加」，不算退回次数 |
| 待验收 → 待办 | 退回并改派 / 不指定 | 清执行人；下一个成员拿到任务描述 + 历次执行结论摘要，不继承别人会话 |
| 进行中 → 待办 | 人取消执行 | 保持现有 |

「退回」不是独立的一列，而是一次转换：看板上表现为「进行中 · 返工 2」，任务卡顶部保留最近一次退回理由（沿用现有 `returnReason`）。

### 执行（run）状态

一张任务下可以有多次执行。每次执行一行：

```text
 [排队] ── 真正开工 ──▶ [执行中] ── 正常交付 ──▶ [交付]
                          │  ▲
                          │  └── 追加 / 人插话（steer，仍是当前执行）
                          ├── 报缺 ──▶ [卡住 · 本次结束]
                          ├── 系统错误 / 超时 / 拒绝 ──▶ [失败 · 本次结束]
                          └── 人取消 ──▶ [已取消]

 [卡住 / 失败] ── 回复 / 重试 ──▶ 新一次 [排队 → 执行中]，同任务同成员接原会话
 [交付] ── 退回 / 追加 ──▶ 新一次 [排队 → 执行中]，同任务同成员接原会话
```

| 字段 | 取值 |
| --- | --- |
| 触发来源 | 派活 / 追加 / 回复后继续 / 退回返工 / 重试 / 认领 |
| 执行人 | 成员 |
| 状态 | 排队 → 执行中 → 交付 / 卡住 / 失败 / 已取消 |
| 耗时 | 从真正开工到结束（#19，排队不计） |
| 附加 | 中途被追加了几次（steer 不产生新行，只在当前行记「+1 追加」）、查看过程 |

任务总耗时 = 各次执行耗时之和；卡住等人的时间不计入任何执行，但卡片上显示「已卡 23 分钟」。

### 与成员头像六态的关系

头像只表「此刻」（不改六态）。任务卡住后本次执行已结束，头像回「闲」或去干别的；「卡住·缺 X」只在看板卡、委派卡和群里那条卡住消息上显示。头像的「卡住」仍指 90 秒无输出或委派失败。两个「卡住」同名但含义不同，见文末待拍板。

## 三、每种状态在群里和看板上显示什么

节点消息以成员本人身份发出，带任务号可点开任务卡；一两行，不带过程细节。

| 状态 | 群里（谁发、文案示例） | 看板卡片 | 委派卡（群主那张） |
| --- | --- | --- | --- |
| 待办（新建） | 不单独发。群主的派活卡上带「#42」 | 待办列；标题、发起方、验收标准 | — |
| 进行中（首次开工） | **Jason**：开工 #42「PWA 断网提示条」，预计 20 分钟内交付。 | 进行中；Jason 头像 + 「执行 1 · 已 3 分」 | 执行中 · 已 3 分 |
| 进行中（排队） | 不发；真正开工时再发「开工」 | 进行中 + 「排队」角标；计时不走 | 排队中 |
| 卡住（成员自报） | **Jason**：#42 卡住了，缺「断网时发送按钮要不要禁用」，@你 定一下。回这条或在任务里回复我就接着做。 | 卡住列；琥珀色描边「⏸ 卡住·缺 产品决定」+ 等谁（你）+ 已卡 N 分 | 卡住 · 缺 产品决定（等你） |
| 卡住（系统失败） | **Jason**：#42 执行超时停了（已做到：写完组件，测试未跑）。可以点重试，我接着做。 | 卡住列；「卡住·执行超时」+「重试」「改派」 | 失败 · 超时（保留现有重试） |
| 进行中（回复后继续） | **Jason**：收到，接着做 #42。 | 回进行中；「执行 2 · 回复后继续」 | 执行中 |
| 待验收 | **Jason**：交付 #42：断网时顶部出现提示条、发送按钮置灰，已加 2 条单测。等验收。 | 待验收列；「通过」「退回」；验收标准对照 | 完成 · 待验收 |
| 完成 | **林经理**（群主）：#42 验收通过（标准 2/2），已完成。 | 完成列 | 已验收 |
| 退回 → 返工 | **你** / 群主：退回 #42：文案改成「网络已断开」，恢复后提示自动消失。<br>**Jason**：收到退回，接着改 #42。 | 进行中「返工 1」；顶部显示退回理由 | 执行中 · 返工 |
| 追加（插入当前执行） | 不发（群主的追加本身就是一条可见委派卡，标「已并入 #42 当前执行」） | 当前执行行「+1 追加」 | 新卡显示「已并入」，不单独回结果 |

群主收到的结果（`delegation-result`）照旧：交付、卡住、失败都会回给发起方；群主据此验收或代答。群主在群里**不复述**成员的交付内容，只发验收结论。

## 四、三种场景的流程

### 1. 群主追加派活（并入 #39）

```text
林经理 delegate(to=Jason, taskId=#42, "顺便加个重连按钮")
  ├─ Jason 正在跑 #42 且发起方相同 → 插入当前执行（steer）
  │     · 不新建执行行，当前行记「+1 追加」，委派卡标「已并入」
  │     · 期限取两者中较长的；不重置原执行开工时间（#19）
  │     · 结果只回一次：当前执行交付时一并回给林经理
  ├─ #42 处于待验收 / 卡住 → 同一成员新开执行（来源「追加」），接上下文
  ├─ Jason 正在跑 #42 但发起方不同（如另一成员）→ 不插入；作为 #42 的下一次执行排队，按 #7/#29 准入
  └─ 没带 taskId → 自动新建一张卡（不会猜测并入哪张旧卡）
```

### 2. 人插话

| 你在哪说 | 成员此刻 | 效果 |
| --- | --- | --- |
| 任务卡里的回复框 | 执行中 | 立刻插入当前执行（你在任务里说话 = 明确对这次活说的） |
| 任务卡回复框 / 回复群里那条卡住消息 | 卡住 | 自动续跑（见第五节） |
| 任务卡回复框 | 待验收 / 完成 | 只记评论，不触发执行；要改就点「退回」 |
| 群里普通发言（不针对任务） | 执行中 | 保持 #28：进入排队，你可以点「转入当前执行」 |

### 3. 返工

1. 待验收时，发起方或你点「退回」，必须写理由。
2. 默认「退回给原成员」：同一成员新开执行（来源「退回返工」），输入 = 退回理由 + 验收标准对照结果；接原会话。
3. 也可选「退回并改派 / 放回待办」：清执行人，新成员拿到任务描述 + 历次执行结论摘要。
4. 返工交付后再回待验收，循环。卡片显示「返工 N」。

## 五、「卡住」由谁解除、怎么解除

**进入**：只有两条路——成员显式调用「报卡住」出口（必须填：缺什么、等谁＝你 / 发起方），或执行失败 / 超时 / 被拒。成员在结果里随口问一句**不算**卡住，仍按交付进待验收，验收人可退回。这样状态不依赖模型自觉写看板（Multica 的反例）。

**谁能解除**

| 谁 | 怎么解除 | 结果 |
| --- | --- | --- |
| 你（任何真人） | 任务卡回复框；或在群里回复那条卡住消息 | 同一成员自动续跑 |
| 发起方（如群主） | 对同一成员、同一 `taskId` 再 `delegate` 一句答复 | 同一成员自动续跑（视为回复） |
| 你 | 点「重试」（系统失败时） | 同一成员续跑，不需要写字 |
| 你 | 「改派」/「取消执行」 | 回待办，清执行人 |
| 其他成员 / 成员自己 | 不能解除 | 避免成员互相接力刷轮次 |

**护栏**
- **拟议护栏、非用户已批准范围**：同一任务连续卡住 3 次（中间没有交付）→ 停止自动续跑，卡片提示「连续卡住 3 次，请你看一下」，只能人来解除。防止群主代答 ↔ 成员再卡住的循环；阈值和是否加由用户拍板，mockup 中仅作标注。
- 群主代答前须确认信息确实在对话里；拿不准就在群里 @你，不替你编答案（写进群主岗位契约，第 4 条借鉴里的短原则）。
- 卡住期间不占并发名额，也不计入执行耗时。

## 六、刷屏控制

群里只发这几类，均为一两行：

1. **开工**：每张任务的首次执行；卡住后续跑、返工开工时发一句「接着做」。
2. **卡住**：每次卡住发一条，必须 @ 等的人。
3. **交付**：每次交付一条（摘要 + 等验收）。
4. **验收结论**：群主或你，一条。

不发：调工具、中间进度、追加被并入、排队、重试中、自动重连。规则：
- 一次执行最多 2 条节点消息（开工 + 卡住/交付）。执行在 60 秒内就结束的，省掉开工，只发交付。
- 群主一次派给 3 个以上成员时，开工合并成一行系统提示「Jason、欧阳 已开工 #42 #43」，卡住/交付仍各自发。
- 嵌套委派（成员再委派，深度 2）的节点不进群，只进上层任务卡的执行记录；唯一例外是需要你回复的「卡住」。
- 节点消息不触发群路由（与 system / group 条目同规则），不会唤醒其他成员。
- 节点消息发到发起这次委派的那个话题；看板仍是根群共享。

## 七、手机端

只读状态为主：群时间线里能看到节点消息；会话页顶部一条「进行中 2 · 卡住 1 · 待验收 1」，点开是按状态分组的只读任务列表（标题、执行人、卡住缺什么）。卡住时可以直接在群里回复那条卡住消息来解除（同桌面）。不提供拖拽、通过 / 退回、改派——这些回桌面做。

## 八、明确不做

- 全员唤醒、成员自己扫看板认领无人指派的卡、心跳 / 主动巡检（Cumora 式）。
- 改跨聊天并行（#29）、同成员准入分类（#7）、计时语义（#19）。
- 把过程直播进群：工具调用、进度百分比、思考过程。
- 自动验收、成员用自己的输出自证完成；系统按「结果里有问句」自动判卡住。
- 新的看门狗、超时自动改派、账号自动回退（已有）。
- 任务依赖图、子任务树 UI、甘特 / 排期视图。
- 外部 IM 推送；手机端完整看板交互。
- 允许其他成员解除别人的卡住、成员之间无限接力。
- 「待补充」不再单独加列，由「卡住」取代（原前 5 第 3 条里拟增的看板态）。

## 九、待技术确认（交 Jason #41）

1. **会话续接**：同任务同成员复用上次的子会话（`childConversationId`）。会话被删、成员换了模型或上下文过长时，是否回退为新会话 + 历次执行结论摘要？压缩策略沿用现有吗？
2. **steer 合并**：发起方 `delegate` 带 `taskId` 命中正在跑的同成员执行时注入当前执行；能否复用 #28 的「转入当前委派」通道？两个委派如何只回一次结果、期限如何取 max 并保持 #19 计时？
3. **「报卡住」出口**：成员侧新工具（字段：缺什么、等谁），调用即结束执行并释放名额。委派状态机是新增 `blocked` 终态，还是 `completed` 加标记？成员在委派中不能用看板工具这一限制不变。
4. **自动续跑的身份和回执**：人回复触发的新执行，发起方记谁（原发起方 / 人）？原发起方那一轮早已结束，交付结果投递到它的新一轮是否会被当成新消息唤醒、是否受 #29 来源聊天约束？
5. **群里回复卡住消息即解除**：现在群消息有没有可靠的「回复某条」关联？没有的话，桌面先只支持任务卡回复框，手机端是否也要放一个回复入口。
6. **系统失败 → 卡住**：改变了现有「失败回待办并清执行人」语义；中断（interrupted）现有「继续 / 重新开始」是否直接映射为卡住卡上的「重试 / 改派」。
7. **自动建卡**：没给 `taskId` 时标题如何生成（截委派首句，不另调模型？）；批量委派（`batchId`）每人一张还是一张多执行？建议每人一张。
8. **节点消息**：成员身份发、但不进路由的新时间线条目类型；是否进其他成员的上下文（建议只进群主上下文的摘要）。
9. **嵌套委派挂卡**：深度 2 的子委派建子任务卡并关联父任务，还是只记在父任务执行记录里。
10. **手机端数据**：看板只读列表能否经 relay 现有同步拿到，还是需要新接口。
11. **连续卡住计数**：按任务计还是按任务 + 成员计；交付后清零。

## 十、待拍板（交用户）

1. 头像六态里的「卡住」（90 秒无输出 / 委派失败）与任务「卡住·缺 X」同名。建议先不改六态，看实际是否混淆；混淆再把头像那态改名「没动静」。
2. 群主是否可以代你回答卡住问题（默认允许，但拿不准必须 @你），还是卡住一律只能人来解除。
3. 60 秒内结束省略「开工」这条阈值是否合适。
